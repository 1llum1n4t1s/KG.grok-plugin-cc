## 2. 同時に伸ばすのが難しい理由

サイズの余裕は 469 bytes です。幅 1 にすると 3,500 bytes 失い、7-Zip も超えます。幅を落としても圧縮は約 5% しか縮みません。したがって「状態を減らせば 1.77 倍が埋まる」は、既に否定されています。

1.77 倍を 1 倍にするには、圧縮時間の約 43% を削り、かつ 469 bytes を超えて大きくしない必要があります。マイクロ最適化と、比較・先読み・キャッシュの局所変更は、記録上おおよそ 0–5% で止まっています。展開は CLI で約 26% 遅い程度で、run によって数 ms が動きます。メモリは今の 2.8 MB では優劣が固定していません。

四指標を一つの変更で同時に超える案は、今の記録からは優先できません。圧縮が主制約、サイズは使い切ると負ける予算、展開とメモリは別の欠損です。

## 3. 案

優先度は、圧縮の 43% に触れる可能性、既存の不採用との距離、安く死ぬか、です。

### 案 1. 幅 2 の決定を保ったまま、byte ごとのオブジェクト展開を一重の価格配列にする

**ボトルネック。** `beam_plan_bt4_active`（`lz.rs` 3307 行、ループは 3338 行）が全位置で frontier、Rep 長、literal / short-rep / rep / match の edge を組み立てます。幅を半分にしてもこの骨格は残ります。

**変えるもの。** wire、確率更新、Rep 履歴の意味、BT5 の候補は維持します。block 内の状態を `BeamActiveNode` の挿入関数列から、位置 × 2 の価格と backpointer の配列へ移し、価格は既存の長さ・距離キャッシュの参照だけにします。出力が 1 byte でも変わったら、その試作は速度比較に進みません。

**仮説。** Standard が同じ機械・同じ入力規模で約 537 ms なのに対し、mode 2 の lazy も beam も約 1 秒です。差の多くが探索アルゴリズムの下限ではなく、1 決定あたりの呼び出しと一時 token だとすれば、決定列を固定した平坦化で圧縮だけが縮みます。展開とサイズは、出力が同じなら変わりません。

**失敗しやすい点。** これまでの出力不変の局所最適化は 3% の速度 gate に届かずに落ちています。Rep の 8 byte 事前判定も paired で 1.0–1.5% でした（438–444 行）。仕事の本体が memcmp と木のポインタ追跡なら、並べ替えでは 43% は出ません。この案は展開もメモリもほぼ動かさないので、単独では総合勝利になりません。

### 案 2. BT の子配列を辞書サイズの循環バッファにする

**ボトルネック。** 子配列は入力長に比例します。Canterbury group では約 22.5 MB で、観測 working set は 36–40 MB 程度に収まっています。Silesia を 1 本の solid にすると、式のうえでは 211,938,580 × 8 ≈ 1.7 GB です。これは未実行の桁見積りです。7-Zip の 64 MiB 辞書は入力長では増えません。

**変えるもの。** 一致候補とフレームは維持し、節の添字だけを辞書窓の剰余にします。窓から落ちた位置は参照しない、という今の距離検査（`bt.rs` 549–551 行）と一致させます。

**仮説。** 開発集合の圧縮は、平均 5.55 訪問でも子配列が L3 より大きいとポインタ追跡が遅れます。循環化で確保量が辞書サイズに頭打ちになり、大入力のメモリ比較が初めて 7-Zip と同じ形になります。訪問回数が既に少ないので、2.8 MB の圧縮が 1.77 倍から 1 倍になる見込みは薄いです。

**失敗しやすい点。** 出力を保った循環 BT は、実質もう一つの matcher 実装です。Exact4 は仕事量の代理値では有利でも、実測は +331 bytes、+4.31% 時間でした。キャッシュが改善しても expand 側の約 7 割が残ります。

### 案 3. 今の token の内側だけ展開を省く、という仮説を計測で先に殺す

**ボトルネック。** 最終 token の開始位置は約 15.5% です。内側の 84% で `bt_frontier` と edge 生成を省ければ、expand が大きいという按分のもとでは圧縮が 7-Zip の付近まで落ちる計算になります。これは仮説です。

**変えるもの。** 最初は何も変えません。現行 parser の token 列に対し、内側位置で frontier と Rep 長を呼ばなかった場合に残る呼出し数だけを数えます。実装は、その割合が gate を超えたあとに限って、出力不変の skip を 1 種類だけ試します。128 byte 即時採用の変更や、nice length 32/128 の再調整は入れません。前者は依存が記録済み、後者は 64 が既にサイズと速度で不採用です。

**仮説。** lazy mode 2 は既に token 長で進み、それでも約 965 ms です。beam との差が約 12% しかないなら、内側 skip の上限もその程度で、43% には届きません。32 byte かつ価格差 512 の被覆 14.09% も、長い一致だけを飛ばすのでは足りないことを示しています。

**失敗しやすい点。** 木は飛ばした位置も後で挿入しないと、後続の候補が変わります。挿入を後回しにすると訪問回数は戻り、producer-consumer 案が不採用になったのと同じ制約です（506–514 行）。`kennedy.xls` のように長い一致が無い範囲では skip がゼロになります。

### 案 4. 展開の CLI 差を、codec 時間と起動時間に分けてからだけ復号側を触る

**ボトルネック。** 同じ 483,130 byte フレームのプロセス内展開は約 30.4 ms、CLI 中央値は 48.9 ms、7-Zip の CLI は 38.9 ms です。この三つは同じ手続きではありません。512 KiB rANS は内部展開を約 25% 縮め、CLI ではまだ約 8% 遅く、圧縮はほぼそのまま、private bytes は増えています。4 lane は内部展開がさらに約 11% 遅くなって不採用です（151–153 行）。

**変えるもの。** 符号器は変えません。既存フレームを、KHC の `decode-bench` と、7-Zip を温めたプロセスで繰り返し展開する計測だけを追加します。codec 時間の差が 15% 未満なら、復号アルゴリズムは主案から外します。15% 以上のときだけ、token 開始時の正規化が 0/1/2 byte のどれかを数えます。2 byte 正規化が bit の 20% 未満なら、そこで打ち切ります。8 byte reservoir は既に約 12% 遅く不採用なので再実装しません。

**仮説。** 展開の見かけの 1.26 倍の一部は、40–60 ms 帯の起動です。残る codec 差が小さければ、総合勝利の条件を「展開アルゴリズムの改良」に置くと、圧縮の 1.77 倍から目が外れます。

**失敗しやすい点。** 7-Zip をプロセス内で同じ境界条件にするのは難しく、起動を引きすぎると自分に有利な分解になります。正規化の集計は圧縮時間を 1 ms も減らしません。

### 共通の実験手続きと holdout

開発入力は `build/khc-current-source-native-solid-20260923-group/all.group` と、manifest の Canterbury 11 ファイルだけにします。Silesia のファイルは開かず、サイズも見ません。閾値も選びません。

7-Zip は 26.03 x64、SHA-256 `EDBEE35370E14030E4C785CF88200F42DC651C1EB4217C1E3963C38A12F099B0`、`compare-solid.ps1` の上記引数、辞書 64 MiB、1 thread です。KHC は同じ辞書・1 thread、Beam/Blended/BT5/W2/B8192/Range です。

指標は、書庫 bytes、warm-up を除く圧縮と展開の中央値、sample した peak working set と private bytes です。圧縮と展開は交互順と逆順の両方を取り、片側だけ速い結果は採用しません。速度の最低単位は、両順序で中央値が 15% 以上縮むこととします。数 % は、同じ binary でも −9% 程度動いた記録があるため使いません（`README.md` 5–7 行）。

サイズの即時不採用は、フレームが 483,599 bytes を 1 byte でも超えることです。出力不変を謳う案は、加えて 483,130 bytes かつフレーム SHA が一致しない場合も不採用です。

メモリは、開発集合で private bytes の中央値が 7-Zip の 1.25 倍を超えたらその案を大入力へ進めません。案 2 だけは、holdout ではない 32 MB の合成列で、辞書 64 MiB の peak private が 7-Zip の 1.5 倍を超えたら不採用です。合成列の勝敗は圧縮率の証拠にしません。

Canterbury でサイズ・両順序の 15%・メモリをすべて通過した案だけ、定数を凍結して Silesia を 1 回測ります。Silesia を見たあとに定数を戻して再測定することは、その案の不採用条件にします。Silesia で四指標が良くても、Canterbury だけの過学習が無いとは言えません。どちらも 1990–2000 年代のコーパスで、既圧縮の現代データや複数 OS は範囲外です。

総合採用は、凍結した同一バイナリで、開発集合と Silesia の両方について、書庫・圧縮中央値・展開中央値・private bytes が 7-Zip 以下、という四つの AND にします。一つでも欠ければ「超えた」とは書きません。

## 4. まず着手する案

案 1 から着手します。幅・Rep 本数・一致長の打ち切り・別符号器は、サイズを 469 bytes より大きく失うか、圧縮を数 % しか動かさないことが既に記録されています。残っている大きい未知は、同じ決定列のまま 1 位置のコストを下げられるか、です。案 3 は lazy が既に遅いので先に死ぬ可能性が高く、案 2 は大入力のメモリ前提で、今の 1.77 倍の主因ではありません。案 4 は展開の見積りを正す計測で、圧縮は変わりません。

手順は次のとおりです。実装で frame を変える段階には、この計測が通ってから入ります。

1. 現行 Release の `profile` で、固定 group の非計測フレームが 483,130 bytes、SHA が `CF4F107BE32E35B603FCA9CE05AC8A5C5C3F4211A4BC0B68236A383F8029447D` と一致することを確認する。一致しなければ以降の時間は無効です。
2. 同じ実行で、`expand_nodes`、`rep_length`、BT 準備の inclusive 時間と、位置数・Rep 長呼出し数を残す。計装時間は速度比較に使わず、割合の判定だけに使います。
3. group の 11 ファイル境界ごとに、その割合が最大のファイルのシェアを記録する。判定には使いません。偏りの有無を後で誤認しないためです。
